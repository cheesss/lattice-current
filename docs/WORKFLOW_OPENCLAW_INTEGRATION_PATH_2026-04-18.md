Parent doc's one-liner:

> "Lattice가 상태와 근거의 본체라면, OpenClaw는 채널/에이전트/운영 orchestration 층이다."

This doc covers the four concrete integration surfaces — channels, TaskFlow,
source repair, scheduler retry, briefing — with file/table pointers.

## Boundary rule (from OPENCLAW_INTEGRATION_ARCHITECTURE §2)

- **Lattice writes state.** NAS tables, `codex_proposals` execution, ingestion.
- **OpenClaw orchestrates.** Channel delivery, multi-step flows, agent role routing.

OpenClaw never writes to NAS directly — it invokes a Lattice tool-call
endpoint, and the Lattice API layer is what mutates state. This keeps the
`system of record` invariant from the parent explainer.

## Four integration surfaces

### 1. Channels (inbound + outbound)

**Inbound**: operator chats with an OpenClaw agent (Slack / Discord /
internal chat). Agent routes based on role keyword (`@ops`, `@research`).

**Outbound**: alerts, digests, and briefings pushed to channels via
webhooks.

Code path:

- `scripts/_shared/openclaw-webhook-emitter.mjs` — emits to the configured
  webhook URL with structured payload (subject, fields, links back to
  Lattice surfaces)
- `scripts/_shared/openclaw-agent-dispatch.mjs` — routes inbound tool
  calls to the correct handler
- Daemon task `generate-followed-theme-briefings` (daily) produces
  briefing payloads that the webhook emitter delivers

### 2. TaskFlow (durable multi-step workflows)

TaskFlow replaces ad-hoc retry scripts for multi-step operator actions.
Typical flow:

1. Operator triggers "investigate incident" from Chat.
2. TaskFlow steps:
   a. OpenClaw calls `get_kpi_summary` → reads from Lattice dashboard API.
   b. OpenClaw calls `get_freshness_report` → identifies stale feeds.
   c. OpenClaw calls `simulate_proposal` for any remediation proposals
      pending in Decision Inbox.
   d. If any simulation passes, OpenClaw escalates to human approval in
      Chat, otherwise marks the incident as observed-only.
3. Final OpenClaw message cites Lattice evidence URLs.

Key point: none of steps a-c mutate state. Only step 2d, via human
approval back into Decision Inbox → `proposal-executor.mjs`, writes.

### 3. Source repair path

Covered as its own workflow in
[WORKFLOW_SOURCE_ADD_PATH_2026-04-18.md](./WORKFLOW_SOURCE_ADD_PATH_2026-04-18.md) §"Self-heal loop".

OpenClaw's involvement is purely **delivery**: when `self-heal-sources.mjs`
emits a `source-repair` proposal, the webhook emitter delivers a
Chat-formatted summary with a "Review in Decision Inbox" link.

Operator still reviews and approves in the Decision Inbox surface.
OpenClaw does not bypass that path.

### 4. Scheduler retry

When a daemon task fails (see `scripts/master-daemon.mjs` error handlers),
OpenClaw can pick up the failure via a webhook and orchestrate retry with
escalation:

- First failure → silent retry in next cron cycle (daemon's own behavior).
- Second failure → webhook to OpenClaw → Chat alert with last 3 log lines.
- Third failure → TaskFlow opens an incident, creates a `runtime_issues`
  row, and pings the operator role assigned to that task domain.

The `automation_actions` and `runtime_issues` tables track this state on
the Lattice side. OpenClaw only reads them for briefing context.

### 5. Briefing

Daily / weekly / incident briefings are generated by:

- `scripts/generate-followed-theme-briefings.mjs` — theme-centric, runs
  daily per followed theme, writes to `followed_theme_briefing_snapshots`
- `scripts/generate-weekly-digest.mjs` — weekly summary across all
  themes, writes to `weekly_digest` surface in the dashboard API
- `scripts/generate-codex-investigation-packet.mjs` — incident-specific
  packet assembled from Lattice evidence for a specific canonical event

OpenClaw webhook emitter delivers these as channel posts with:

- Subject line
- 3-5 top findings
- Deep-link back into Investigate surface for each finding
- Citation list (article IDs, evidence sources)

## Tool-call surface exposed to OpenClaw

All read-only. Served by `event-dashboard-api.mjs`:

| Tool name | What it returns |
|---|---|
| `get_health` | Runtime + data quality health summary |
| `get_kpi_summary` | Current KPI strip (signals + nowcast fuse) |
| `get_approval_queue` | Pending approvals for the operator |
| `get_theme_brief` | Theme brief with evidence + citations |
| `get_freshness_report` | Per-signal / per-source freshness audit |
| `simulate_proposal` | Dry-run of a proposed action |

Mutating tools (execute_proposal, approve_proposal) **exist** but are
gated — OpenClaw cannot call them directly. They require a human-in-loop
approval click in the Decision Inbox first. The execute tool only
proceeds for rows already `status='approved'`.

## Key tables

| Table | Role |
|---|---|
| `automation_actions` | Audit log of system-initiated actions (retry, escalate, notify) |
| `runtime_issues` | Incidents surfaced from daemon failures |
| `followed_theme_briefing_snapshots` | Daily theme briefing payloads |
| `codex_proposals` | Proposals OpenClaw can read but only humans approve |
| `approval_queue` | Human-review queue state |

## Operational gotchas

- **Do not let OpenClaw call mutating tools without Decision Inbox review.**
  The boundary rule in §2 exists for a reason — OpenClaw is an
  orchestration layer, not a replacement for operator judgment.
- **Webhook delivery is fire-and-forget** from Lattice's perspective. If
  the OpenClaw endpoint is down, the briefing is logged to
  `automation_actions` with `status='webhook_failed'` and the operator
  can re-trigger from Ops surface.
- **Agent role routing** happens entirely on OpenClaw side. Lattice
  doesn't know which agent instance is handling a given channel post.
  That's by design — Lattice's tool surface is stateless per call.
